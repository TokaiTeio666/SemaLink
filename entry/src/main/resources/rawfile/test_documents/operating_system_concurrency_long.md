# 操作系统并发：从进程隔离到线程协作

并发系统首先要回答“谁拥有资源”。进程通常拥有独立虚拟地址空间、文件描述符表和安全边界，线程则共享所属进程的大部分资源。创建进程的隔离成本较高，但故障传播范围更清晰；创建线程较轻量，却要求开发者谨慎处理共享状态。设计服务时不能只比较创建速度，还要同时考虑恢复策略、权限边界、可观测性和部署方式。

线程调度把可运行任务映射到处理器。操作系统维护就绪、运行、阻塞等状态，并在时间片到期、中断到达或线程主动等待时切换执行上下文。上下文切换需要保存寄存器、栈指针和调度信息，也可能破坏缓存局部性。大量短任务若无节制地创建线程，会让调度和内存开销超过实际计算，因此线程池需要限制并发度并提供排队策略。

共享内存带来数据竞争。当两个线程没有同步地访问同一可变数据，并且至少一个访问是写操作时，最终结果可能依赖不可复现的执行顺序。锁通过互斥临界区建立先后关系，但锁只保护约定范围内的数据；遗漏一次加锁或在不同位置使用不同锁，都会使保护失效。工程上应明确每个字段由哪把锁保护，并尽量缩小临界区。

互斥锁解决排他访问，却不能表达所有等待条件。条件变量允许线程在条件不满足时释放互斥锁并休眠，条件改变后再被唤醒。被唤醒不代表条件必然成立，因为可能存在虚假唤醒，也可能被其他线程先一步消费。因此等待方必须在循环中重新检查谓词，而通知方应先在锁保护下完成状态更新，再发送通知。

信号量用计数表示可用许可，适合限制同时访问稀缺资源的任务数量。例如连接池容量为八时，初始许可可设为八；任务进入前获取许可，退出时归还。若归还发生在异常路径之外，就会永久泄漏许可并造成系统停滞。因此资源获取与释放必须使用结构化清理，测试也要覆盖取消、超时和异常返回。

读写锁允许多个读者并发进入，同时保持写者排他。它适合读取明显多于写入、且读临界区足够长的场景。若临界区很短，额外状态维护可能比普通互斥锁更贵；若实现偏向读者，写者还可能长期饥饿。选择同步原语前应使用真实工作负载测量，而不是依据名称推断收益。

死锁通常需要互斥、占有并等待、不可剥夺和循环等待四个条件同时存在。统一锁顺序能破坏循环等待，是最容易审查的预防方式。另一种做法是带超时地尝试获取锁，失败后释放已持有资源并重试，但重试可能引入活锁。监控应记录锁等待时间和持有时间，日志不能包含业务敏感数据。

无锁算法依赖原子读改写操作与内存顺序。一次原子比较交换只能保证目标位置的更新不可分割，并不会自动让复杂对象的全部不变量安全。ABA 问题、对象回收和缓存一致性都会增加证明难度。在普通业务代码中，清晰的消息传递或短临界区锁通常更容易维护；只有性能证据明确时才值得引入无锁结构。

消息队列把共享状态转换为事件所有权。生产者提交不可变消息，消费者串行处理某类状态，可以显著减少锁数量。不过队列必须定义容量、背压和关闭语义。无界队列会把流量峰值变成内存风险；直接丢弃会破坏业务正确性；持续阻塞又可能把拥塞扩散到调用链。合理策略要结合任务优先级和可重试性。

取消是并发协议的一部分。调用方取消任务后，工作线程应在安全检查点停止，释放锁、文件和许可，并避免把半完成结果发布给后续阶段。取消标志本身需要可见性保证，阻塞等待也需要能被唤醒。只在函数入口检查一次取消状态不足以处理长循环或多阶段操作。

并发测试不能依赖固定休眠来猜测执行时序。更稳定的方法是使用屏障、闩锁或可控调度点，让测试精确推动线程进入目标状态。测试应覆盖重复执行、超时、取消、异常、队列满和资源耗尽，并验证最终不变量。检测到偶发失败时，应保存随机种子或事件顺序以便重放，但生产调度算法本身不应依赖随机结果决定正确性。

可观测性需要区分吞吐量、排队时间、执行时间和锁等待时间。仅观察平均延迟会掩盖长尾阻塞，应该同时记录分位数和超时数量。线程数不断增加而吞吐量不升，通常意味着锁竞争、外部资源上限或上下文切换成本已经成为瓶颈。诊断时先定位等待关系，再决定扩大线程池还是减少共享。

进程间通信可采用管道、消息通道、共享内存或套接字。共享内存吞吐量高，但同步和生命周期管理更复杂；消息通道边界清楚，序列化成本却不可忽略。跨设备场景还要面对断连、重复消息和版本差异，因此不能把本机线程通信的假设直接套到网络协议。

一个稳健的并发模块应把状态机、资源所有权和错误语义写进接口。调用者需要知道操作是否幂等、超时后是否仍可能完成、回调在哪个执行上下文触发，以及关闭后哪些方法仍可调用。清楚的契约比某个特定锁实现更重要，因为实现可以替换，跨模块承诺却会长期存在。

最终评审应从正确性开始：共享不变量是否受保护，所有退出路径是否释放资源，是否存在循环等待，取消是否可传播。随后才是性能：临界区是否过长，队列是否有界，线程数量是否与负载匹配。把这些问题与真实指标、压力测试和故障注入结合，才能形成可复现的并发工程结论。
