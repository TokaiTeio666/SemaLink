# SemaLink 无固定中心全互联控制通道设计

**日期：** 2026-07-23

## 1. 目标

SemaLink 需要移除多设备通信中的固定中心假设。每台可信设备运行完全相同的运行时，自动与其他所有当前可用的可信设备建立直接控制连接，并且都能独立发起查询，聚合本机知识与所有可用远端设备的知识。

设计必须满足以下结果：

- 不存在永久协调器、主设备或特权设备。
- 任意一对在线可信设备最终收敛为一条有效控制会话。
- 任意设备都能成为某一次查询的临时协调方。
- 查询使用本机知识库以及查询开始时所有可用远端节点。
- 单台设备失败、离线或响应缓慢时，不阻断本机及其他设备的结果。
- 拓扑适用于任意数量的可信设备，而不是只支持三台演示设备。

当可用设备数量为 `N` 时，完整逻辑拓扑包含 `N * (N - 1) / 2` 条直接连接。

## 2. 非目标

- 不支持通过中间设备转发查询的多跳路由。
- 不选举领导者、主设备、注册中心或长期中心节点。
- 不在 HarmonyOS 可信设备能力之外自行实现设备发现。
- 不在每次查询结束后关闭健康的全互联通道。
- 不替换现有任务、证据、隐私和充分性评估协议。

## 3. 当前基础

现有代码已经具备大部分点对点通信能力：

- `DskControlHub` 能按远端设备 ID 隔离并维护多条入站和出站会话。
- `PeerConnectionPool` 能为每台远端设备维护独立的数据绑定和通道状态。
- `PeerTaskResponder` 能接收远端任务并查询本机知识提供器。
- `MultiDeviceTaskCoordinator` 能并行查询本机候选和已就绪的远端候选。
- `AppRuntime.refreshAvailableDevices(true)` 已能发现并连接所有可见设备，但生命周期和测试仍以单一主发起设备为中心。

目前缺少的能力包括：稳定的本机身份、确定性的设备对拨号所有权、持续拓扑协调、重复会话收敛，以及从每台设备发起查询的对称测试。

## 4. 总体架构

每台设备运行相同的组件栈：

```text
AppRuntime
  -> PeerMeshOrchestrator
       -> DeviceTopologyProvider
       -> PeerMeshPlanner
       -> Task3TlsCoordinator
            -> DskControlHub
            -> PeerConnectionPool
  -> MultiDeviceTaskCoordinator
  -> PeerTaskResponder
```

### 4.1 DeviceTopologyProvider

新增生产环境拓扑提供器，在自身生命周期内持有一个 HarmonyOS `distributedDeviceManager.DeviceManager`，并暴露以下接口：

```ts
interface DeviceTopologySnapshot {
  localDeviceId: string;
  peers: PeerDevice[];
}

interface DeviceTopologyProvider {
  start(onChanged: () => void): void;
  snapshot(): Promise<DeviceTopologySnapshot>;
  stop(): void;
}
```

本机身份使用 `DeviceManager.getLocalDeviceNetworkId()`。远端身份继续优先使用 `networkId`，确保本机标识、远端标识和 DSK 协作会话处于同一标识域。空的本机或远端 ID 均视为无效，不参与拓扑规划。

拓扑提供器订阅可信设备状态变化，并在通知网格协调器之前合并短时间内的事件突发。现有 `TrustedDeviceResolver` 通过适配器继续返回 `snapshot().peers`，避免立即重写现有查询和测试依赖。

### 4.2 PeerMeshPlanner

`PeerMeshPlanner` 是不包含副作用的纯组件。它针对每个远端节点比较稳定的本机和远端 ID：

```text
localDeviceId < remoteDeviceId  -> PRIMARY_DIALER
localDeviceId > remoteDeviceId  -> INBOUND_WAITER
localDeviceId == remoteDeviceId -> INVALID_SELF
```

假设三台设备满足 `A < B < C`，主拨号边严格为 `A -> B`、`A -> C` 和 `B -> C`。这样不需要中心节点，也能确保每个无序设备对只由一侧主动拨号。

### 4.3 PeerMeshOrchestrator

`PeerMeshOrchestrator` 负责设备发现协调、入站等待宽限计时器和重试计时器。生产运行时中，只有该组件可以决定是否主动建立某条控制连接。

接口如下：

```ts
start(): Promise<void>;
reconcile(trigger: MeshTrigger): Promise<void>;
ensureReady(waitBudgetMs: number): Promise<string[]>;
destroy(): void;
```

`reconcile` 必须串行执行。多个并发触发只设置一次脏标记，并在当前协调结束后额外执行一轮，不能同时修改设备目录和连接状态。

针对最新快照中的每个远端设备，协调器执行以下操作：

1. 将设备注册到 `Task3TlsCoordinator` 和 `PeerConnectionPool`。
2. 规划结果为 `PRIMARY_DIALER` 时立即主动连接。
3. 规划结果为 `INBOUND_WAITER` 时等待对端入站连接。
4. 入站等待方尚未就绪时启动 3000 毫秒宽限计时器。
5. 宽限时间结束仍未收到入站连接时，允许发起临时兜底出站连接。
6. 设备就绪或从拓扑中移除时，取消对应宽限和重试计时器。

被移除设备必须独立断开，协调过程不得关闭其他设备的健康会话。

### 4.4 规范会话选择

宽限超时后的兜底连接可能短暂产生两条物理会话，但 `DskControlHub` 对上层始终只暴露每台远端设备的一条有效会话。

每条 `DskControlHub` 会话记录：

- 远端设备 ID；
- `INBOUND` 或 `OUTBOUND` 方向；
- 会话 ID 和创建顺序；
- 当前连接状态。

首选方向使用与拨号规划相同的规则：

```text
localDeviceId < remoteDeviceId  -> 优先 OUTBOUND
localDeviceId > remoteDeviceId  -> 优先 INBOUND
```

首选会话就绪前，已有的非首选就绪会话可以作为临时会话使用。首选会话就绪后，Hub 原子切换后续发送目标，再关闭该设备的其他会话。这样既保留可用性，也能确定性地收敛到唯一规范会话。

控制消息去重从“每条会话一个集合”调整为“每台远端设备一个有界缓存”。缓存按插入顺序保留最近 256 个消息 ID，确保同一消息通过两条临时会话到达时只处理一次，同时避免集合无限增长。

## 5. 生命周期与拓扑协调

获得分布式设备权限后启动网格。以下事件触发拓扑协调：

- 首次获得权限；
- 应用进入前台；
- 可信设备上线或离线通知；
- 控制通道或数据绑定失败；
- 用户或系统显式刷新设备；
- 自动多设备查询开始前。

设备通知在 300 毫秒内合并。进入前台和查询前刷新不等待现有重试延迟，直接触发一次立即协调。

每台远端设备遵循以下逻辑状态流转：

```text
DISCOVERED
  -> CONNECTING            本机是主拨号方
  -> WAITING_INBOUND       本机等待入站
WAITING_INBOUND
  -> CONNECTING            宽限超时后兜底
CONNECTING
  -> BINDING               控制会话就绪
BINDING
  -> READY                 数据绑定确认
READY
  -> BACKOFF               传输或绑定失败
  -> DISCONNECTED          设备不再可用
BACKOFF
  -> CONNECTING            重试到期或立即生命周期触发
DISCONNECTED
  -> DISCOVERED            设备重新上线
```

每台设备独立维护重试状态。连接失败后的延迟依次为 1、2、4、8 秒，后续重试上限为 30 秒。进入 `READY` 后清零失败次数。应用进入前台或设备重新上线时，可以取消当前等待并立即重试。

## 6. 查询流程

任意设备都执行相同的查询流程：

1. 构建语义任务并进入路由阶段。
2. 调用 `PeerMeshOrchestrator.ensureReady(3000)`，触发拓扑协调并最多等待三秒。
3. 固化本次任务使用的就绪远端设备列表。
4. 候选集合由 `local` 和固化后的所有远端设备组成。
5. 并行执行本机检索和远端任务。
6. 聚合所有已完成来源返回的证据。
7. 单独记录未参与、失败或超时的设备。
8. 使用现有任务充分性评估器判断已经到达的证据是否足够。

三秒拓扑准备预算不能被 30 秒的数据绑定等待放大。后台连接可以继续，但当前查询只使用准备预算内进入 `READY` 的设备。

查询发起设备只在当前任务内承担临时协调职责。同一个运行时始终保留响应器能力，可以同时响应其他设备发起的任务。

查询结束后保持健康网格连接，避免后续查询重复承担建链延迟。

## 7. 异常处理

### 7.1 本机身份获取失败

运行时无法取得非空本机网络 ID 时，禁止主动网格拨号，并报告 `E_LOCAL_DEVICE_ID_UNAVAILABLE`。系统可信的入站协作请求仍可接受，但运行时不得在缺少稳定身份时作出可能冲突的拨号所有权判断。

### 7.2 远端连接或绑定失败

失败只更新对应设备并安排该设备重试，其他设备保持就绪并继续作为查询候选。已有 `AppError` 系统错误码应保留；没有明确错误码时，根据阶段使用 `E_CONNECT_FAILED` 或 `E_DSK_BIND_FAILED`。

### 7.3 远端查询失败

单台远端设备超时、断线、协议异常或返回空结果时，只结束该设备的查询分支，不能拒绝整个查询。本机检索始终执行。最终结果仍可能语义上不充分，但不得把证据不足误报为整个传输系统失败。

### 7.4 设备移除

远端设备从可信可用设备快照中消失时，运行时取消该设备的宽限计时器、重试计时器、绑定等待器和待处理任务等待器，然后只关闭该设备的会话。

### 7.5 运行时销毁

销毁时停止设备监听，禁止新的拓扑协调，取消所有计时器和等待器，销毁响应器及查询传输对象，并确保每条剩余 Hub 会话只关闭一次。

## 8. 安全边界

网格只使用 HarmonyOS 可信设备发现与 DSK 协作能力。入站会话必须继续提供系统协作令牌和 SemaLink 指定通道标识。本功能不增加公开设备发现、中继传输、多跳路由或任意网络节点接入。

## 9. 状态与界面投影

现有逐设备状态投影继续作为界面状态来源，分别展示每台设备的控制通道和数据通道状态。

界面不得再把任何设备标记为中心。在三设备部署中，网格健康时每台设备都应显示另外两台设备，活动节点数为 2。查询历史记录本次实际使用的来源设备，并单独列出被排除的设备。

## 10. 测试策略

### 10.1 单元测试

- 规划器稳定返回 `PRIMARY_DIALER`、`INBOUND_WAITER` 和 `INVALID_SELF`。
- 三台设备严格产生三条预期主拨号边。
- 四台设备产生六条不重复主拨号边。
- 拓扑协调串行执行并合并并发触发。
- 仅未就绪的入站等待方启动宽限计时器。
- 收到就绪入站会话后取消兜底计时器。
- 重试延迟符合 1、2、4、8、30 秒，并在成功后清零。
- 移除一台设备时只取消该设备的资源。
- 规范会话方向严格由稳定设备 ID 决定。
- 首选会话就绪前，临时会话保持可用。
- 相同控制消息通过两条会话到达时只分发一次。
- 每台设备的去重缓存始终不超过 256 项。

### 10.2 运行时与集成测试

- A、B、C 同时启动后，每个设备对收敛为一条有效连接。
- 主连接延迟并触发兜底后，最终收敛且不丢消息。
- A、B、C 分别发起查询时，都能查询另外两台设备。
- 每次查询都能聚合本机证据与互补远端证据。
- 单台远端超时或断线不丢弃其他设备证据。
- 新设备上线时加入网格，不重连已有健康设备。
- 设备离线时退出网格，不改变无关连接。
- 前台恢复时立即重试失败设备。
- 连续十轮查询和重连后，不残留等待器、计时器或会话。
- 现有单设备、自动查询、控制 Hub、连接池和协议测试继续通过。

### 10.3 三真机验收

在三台互信设备上安装同一个 HAP，并将三个应用都置于前台。满足以下条件时验收通过：

1. 每台设备都显示另外两台设备。
2. 不需要手动选择中心，每台设备均达到两个活动节点。
3. 从 A 发起查询时，可以使用 A、B、C 的合格证据。
4. 从 B、C 分别发起查询时结果同样成立。
5. 一台设备离线后，另外两台仍保持连接并可相互查询。
6. 离线设备重新进入前台后，缺失的两条连接自动恢复。
7. 日志中不存在长期重复会话或失控的重试循环。

## 11. 预期代码边界

实现范围集中在以下区域：

- 在 `entry/src/main/ets/communication/` 下新增拓扑提供器、纯网格规划器和网格协调器。
- 扩展 `DskControlHub`，加入本机身份、会话方向、规范会话选择和逐设备有界消息去重。
- 调整 `Task3TlsCoordinator`，使其负责注册入站及发现设备，但不再独立决定网格拨号所有权。
- `AppRuntime` 将生产环境设备发现和连接生命周期委托给网格协调器，同时保留测试所需的可注入解析器兼容性。
- `EntryAbility` 在权限通过后启动网格，并在应用进入前台时刷新网格。
- 扩展多设备测试夹具，使每台模拟设备都同时拥有协调器和响应器。

与本功能无关的界面重构、协议替换和知识索引修改不在实现范围内。
