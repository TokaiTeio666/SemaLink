# SemaLink 跨设备协作记录 UI 设计

## 状态

已获用户确认，准备进入实现计划阶段。

## 背景

SemaLink 当前已有本地知识库、语义查询和跨设备通信能力。现有入口页面将知识库、连接状态、查询输入、结果和错误信息按纵向区域展示，但缺少对跨设备协作过程的回顾和继续操作能力。

本设计将“跨设备协作中心”作为 UI 的重点，采用“协作记录优先”的信息架构，以“列表 + 详情”为主要布局，并将“继续查询”作为详情页的首要操作。

## 目标

- 让用户快速浏览最近的跨设备协作记录。
- 让用户查看一条记录的设备、状态、查询内容和知识证据。
- 让用户从历史记录恢复原查询上下文并继续提问。
- 清晰表达在线、同步中、离线、发送失败和查询超时等状态。
- 在手机和更宽的设备上都保持可读、可操作的布局。
- 第一版只保留当前应用运行期间的记录，不引入持久化迁移。

## 非目标

- 不修改现有通信协议和消息格式。
- 不重写 `SessionManager` 的连接、ACK、结果和超时机制。
- 不在第一版加入跨应用分享、记录搜索、批量删除或云端同步。
- 不替换现有本地知识库检索流程。

## 用户流程

1. 用户打开 SemaLink，在跨设备协作区域看到最近记录和当前设备连接状态。
2. 用户点击左侧或列表中的一条记录。
3. 详情区域展示查询内容、来源设备、目标设备、当前状态、摘要和证据数量。
4. 用户点击“继续查询”。
5. 系统恢复该记录的原查询上下文，将用户带回语义查询区域。
6. 用户补充问题并发起新的查询。
7. 新查询根据成功、失败、断开或超时结果生成新的协作记录。

## 页面结构

### 页面顶部

- 页面标题：协作记录。
- 当前连接状态：在线、连接中、处理中、已断开或错误。
- 已连接设备名称和脱敏设备标识。
- 可选的时间范围筛选入口，第一版只提供当前运行记录。

### 记录列表

列表按时间倒序排列，每一项展示：

- 查询标题或问题摘要。
- 发起设备和目标设备。
- 发生时间。
- 记录状态。
- 证据数量或结果摘要的简短提示。

选中项使用稳定的视觉状态标识。列表为空时显示空状态，并引导用户先连接设备和发起查询。

### 详情区域

详情区域展示当前选中记录的完整信息：

- 原始查询内容。
- 来源设备、目标设备和同步状态。
- 查询摘要。
- 证据数量及可读的证据片段。
- 主要操作“继续查询”。
- 次要操作“重新发送”，仅在记录发送失败或目标设备离线时显示。
- 可选的“查看原文”入口，复用现有知识结果的展示方式。

### 响应式布局

- 平板或宽屏：使用左右分栏，左侧记录列表，右侧详情。
- 手机：默认显示记录列表，点击记录后进入详情视图；详情提供返回列表动作。
- 所有按钮和状态文本保持固定的最小高度，避免状态变化造成布局跳动。

## 状态与交互

记录状态包括：

- `SENDING`：查询或协作内容正在发送。
- `SYNCED`：目标设备已确认接收或打开。
- `OFFLINE`：目标设备当前不在线，但本地记录和上下文仍保留。
- `FAILED`：发送、协议处理或查询失败，可尝试重新发送。
- `TIMEOUT`：等待 ACK 或结果超时，保留原问题并提示重试。

连接状态继续使用现有 `ConnectionState`，UI 通过 `AppSnapshot` 的状态更新显示连接提示，不复制一套连接状态机。

“继续查询”只恢复记录中的原问题和必要上下文，不自动提交新请求。用户可以编辑内容后再提交，避免误触发网络或设备操作。

## 实现边界

### UI 组件

- 在 `Index.ets` 中保留现有页面入口和生命周期订阅。
- 新增独立的协作记录列表组件，负责列表渲染、选中状态和空状态。
- 新增独立的协作记录详情组件，负责详情展示和操作按钮。
- 使用父级页面协调选中记录与“继续查询”动作，避免列表和详情直接依赖通信实现。

### 状态管理

- 新增 `CollaborationRecord` 模型，建议放在独立的协作领域模型文件中。
- `AppSnapshot` 增加当前运行记录集合和选中记录标识。
- `AppStateStore` 负责发布记录集合和选中项变化。
- `AppRuntime` 在查询生命周期结束时创建或更新记录。
- 第一版记录只存在内存中，不写入 RDB，也不修改数据库结构。

### 通信复用

- `SessionManager` 继续负责连接建立、ACK、结果、错误和超时。
- `QueryCoordinator` 或 `AppRuntime` 将 `SessionManager` 的结果映射为协作记录状态。
- 不新增协议消息类型，不改变现有 `ProtocolEnvelope`、`QueryPayload` 或 `ResultPayload` 合同。

## 数据流

```text
用户发起查询
  -> QueryCoordinator / AppRuntime
  -> SessionManager.execute
  -> 结果、错误或超时
  -> 生成 CollaborationRecord
  -> AppStateStore.update
  -> Index.ets 重新渲染列表和详情
  -> 用户点击继续查询
  -> 恢复原问题与上下文
```

记录更新必须覆盖以下边界：

- 请求开始时创建 `SENDING` 记录。
- 收到成功结果时更新为 `SYNCED`，写入摘要和证据数量。
- 连接断开、发送错误或协议错误时更新为 `FAILED` 或 `OFFLINE`。
- ACK 或结果超时时更新为 `TIMEOUT`。
- 重试使用同一条用户意图创建新的尝试记录，保留失败记录用于追踪。

## 错误处理

- 设备离线：详情显示设备离线原因和最后在线时间；“继续查询”仍可用于本机上下文，但跨设备发送动作保持禁用。
- 发送失败：显示明确错误信息和“重新发送”，不清空查询内容。
- 查询超时：显示超时阶段，允许用户继续查询或重新发送。
- 记录内容缺失：详情显示可恢复的最小信息，并禁用依赖证据的操作。
- 状态更新失败：保留当前 UI 状态，同时通过现有错误区域展示可读错误。

## 测试与验收

### 单元测试

- 新建记录时字段和初始状态正确。
- 成功结果能将记录更新为 `SYNCED`，并保存摘要和证据数量。
- 发送错误、断开和超时分别映射到正确的失败状态。
- 选中记录变化只影响当前详情，不改变其他记录。
- “继续查询”返回原问题和上下文，且不会自动提交请求。

### UI 测试

- 空记录列表显示空状态。
- 列表选中项能正确加载详情。
- 成功、失败、离线和超时记录的状态文案和操作按钮正确。
- 手机布局能在列表和详情之间切换。
- 宽屏布局同时展示列表和详情，文本不重叠或溢出。
- 现有知识库查询、跨设备连接和断开流程保持通过。

### 验收标准

- 用户能从协作记录进入详情并继续查询。
- 用户能看懂当前协作是否完成、失败或等待重试。
- 记录在应用运行期间不会因普通状态刷新丢失。
- 第一版不需要数据库迁移即可运行。
- 现有测试套件没有回归。

## 后续扩展

在第一版稳定后，可以单独规划记录持久化、历史搜索、按设备筛选、批量清理和跨设备记录同步。这些能力不属于本次 UI 设计的实现范围。
